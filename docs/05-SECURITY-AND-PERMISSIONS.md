# Security, permissions and data flow

## Permission matrix

All rows require current business/site membership and active employment grant for the action. Use separate grants when combining duties. The server can return scoped current state on a conflict. Denied scopes receive a generic response without protected record fields.

| Action                                                 | Picker                        | Packer              | Handoff operator         | Supervisor                       | Support viewer                  |
| ------------------------------------------------------ | ----------------------------- | ------------------- | ------------------------ | -------------------------------- | ------------------------------- |
| Read authorized queue, detail and visible history      | Available work and own claims | Pack-relevant views | Handoff and return views | Site operations                  | Status and permitted timestamps |
| Enter and commit a manual release                      | —                             | —                   | —                        | Yes                              | —                               |
| Claim/work, partial pick, report shortage              | Active own claim              | —                   | —                        | Separate picker grant            | —                               |
| Release claim / reassign / resolve shortage            | Release own unstarted claim   | —                   | —                        | Reassign or resolve with reason  | —                               |
| Verify and seal package                                | —                             | Yes                 | —                        | Separate packer grant            | —                               |
| Confirm observed pickup                                | —                             | —                   | Yes                      | Separate handoff grant           | —                               |
| Cancel pre-handoff / decide return disposition         | —                             | —                   | —                        | Yes                              | —                               |
| Receive and inspect authorized returns                 | —                             | —                   | Yes                      | Separate receiving grant         | —                               |
| Export records, subscribe or replay an upstream effect | —                             | —                   | —                        | Separately approved later grants | —                               |

The business owner administers enrollment and grants. Operating roles are assigned explicitly, including for owners. Bootstrap is a local operator-only, one-use entry point that creates one owner and one site. Use single-use, expiring invitations and supervised recovery, benchmark Argon2id for passwords, and store only hashed opaque session tokens with expiry and revocation. Propose a 12-hour absolute session lifetime and a 30-minute idle lock, subject to field approval. Recheck membership after foreground reauthentication and before receipt replay. Revocation and last-owner protection need durable integration tests. Keep explicit login/session rate and concurrency budgets. An eventual platform integration needs approved OAuth authorization code with PKCE S256 in the system browser, verified issuer/audience/redirect/state/nonce and current server membership validation. [Native OAuth guidance](https://www.rfc-editor.org/rfc/rfc8252)

## Boundaries and protection

Validate route, body, headers and content type, cap streamed request bytes and query time, use parameterized SQL and database roles with minimal grants. Give health and readiness minimal responses. Use a bounded correlation ID and diagnostic log. Test denied variants and expiry across both reads and writes. Local API/DB bind loopback. A free-standing release that connects remotely requires verified HTTPS, trusted certificates and a network exit allowlist. Physical ADB reverse is for the authorized debug target only. User-facing status derives from validated, machine-readable server codes.

| Data                                              | Destination and trigger                                                          | Lifetime and deletion                                                                                                                                                                                            |
| ------------------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Password/enrollment token                         | Local API on user submission. Password hashes in PostgreSQL.                     | Discard raw inputs after verification. Revoke invitations and sessions after recovery where applicable.                                                                                                          |
| Opaque session secret                             | Native OS-backed SecureStore after authenticating.                               | Remove on sign-out or revocation. Reverify on resume. [SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/)                                                                                     |
| Minimal work refs, draft counts and operation IDs | Scoped SQLite on authorized fetch and explicit draft/save or submit preparation. | Bound by user/site/store, at most 24 hours for replay. Exclude from backup and transfer. Purge scoped records and keys at sign-out after unsettled commands are resolved or handed to supervised reconciliation. |
| Release refs, pick/pack/handoff facts and returns | Dedicated PostgreSQL after verified commands.                                    | Owner sets approved retention before real records. Local QA can remove only disposable datasets. Backups are owned, access-controlled and tested in an isolated restore.                                         |
| Screen and camera                                 | Managed native lifecycle on active page and user approval.                       | Accept only supported barcode text, preserve leading zeros, release camera on blur. No photos, frame uploads, microphone, location, crash uploads or remote analytics in the proposed slice.                     |
| Operational diagnostics                           | Local log on command, storage or readiness errors.                               | Scrub tokens, personal data, payloads and scan content. Bound rotation and document ownership.                                                                                                                   |

Plain Expo SQLite is acceptable for minimal synthetic-only design validation. It does not encrypt files by itself. Prior to real data, verify SQLCipher or equivalent platform storage, key lifecycle, OS backup and transfer exclusions, remanence, shared-device lock, screenshots/recents and device loss response on packaged Android/iOS. Require a current authenticated session before rendering locked content. Link inputs use an allowlisted typed route and opaque IDs. Do not place data, receipts, roles or session credentials in links. [Expo SQLite](https://docs.expo.dev/versions/v58.0.0/sdk/sqlite/) · [Native security baseline](https://mas.owasp.org/MASVS/)

The local operations owner reviews readiness failures, unsettled work and storage warnings. Final alert thresholds, access, backup retention, recovery point and recovery time require measured local restore evidence and owner approval before an operational pilot.
