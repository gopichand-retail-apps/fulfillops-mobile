# OrderFlow screen design

**Proposed wireframes · November 24, 2026**

## Layout and interaction

Use a native task stack with **Work** as the landing route. Supervisors enter **Release** and **Exceptions** from the site queue. Support opens the read-only queue and history. Returns are reached from completed handoff or the site returns list. The site and freshness indicator stay reachable from work screens. Back returns to the previous step, restores focus and preserves position. Explicit confirmation is required for cancellation, partial release, and handoff.

| Reference reviewed                          | Pattern considered                                                                        | Application to OrderFlow                                                                                                                                                                                                                                          |
| ------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Microsoft Dynamics 365 Warehouse Management | Work grouping, directed scans and short-pick handling.                                    | Keep instructions at the input and the Shortage action visible. Use one current job on compact devices instead of clustering many. [Mobile menu items](https://learn.microsoft.com/en-us/dynamics365/supply-chain/warehousing/configure-mobile-devices-warehouse) |
| Oracle Warehouse Management 26B             | Location-first task execution and explicit drop confirmation.                             | Keep bin, item, quantity and next confirmation in the same vertical path. Separate package sealing from observed handoff. [Zone picking](https://docs.oracle.com/en/cloud/saas/warehouse-management/26b/owmol/executing-pick-zone-tasks-in-the-rf.html)           |
| ERPNext                                     | Pick-list barcode checking with an explicit quantity prompt and downstream delivery step. | Normalize scan/manual input to the same candidate. Keep confirmation deliberate and preserve exact barcode strings. [Pick List](https://docs.frappe.io/erpnext/pick-list)                                                                                         |

References inform workflow only. All wireframes, artwork and copy are original. Vendor artwork, logos and screen assets have no planned reuse.

Compare a focused native queue-to-detail stack with a permanent dense workbench. The stack keeps scan control, status and confirmation legible on handhelds and is the compact default. A workbench is useful when supervisors and packers compare queue and detail on a wide tablet. Use the same actions in an adaptive split view when both panes remain legible.

## Shared components and tokens

Use native system type with tabular quantities. Base metadata 13, supporting body 16, section heading 20 and current-line quantity 28 logical units, all scalable. Spacing scale 4/8/12/16/24/32. Light uses background `#F6F6FB`, text `#202137`, primary `#403B86` with white button text. Dark uses `#171726`, foreground `#F4F2FF`, primary `#C4C0FF` with `#171726` button text. Proposed warning and danger text are `#7A4300` and `#9B2335` on light, `#FFD08A` and `#FFAAAF` on dark. Use text and accessible names with status color. Verify representative states and overlays for contrast.

| Component ID      | Behavior                                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| C01 Site header   | Site switcher, title and connection/freshness status. Hide prior site content immediately when changing scope.     |
| C02 Status        | Text label, accessible name and optional timestamp. Announce meaningful commits and errors once.                   |
| C03 Quantity pair | Committed/required quantities, labeled units and a textual remainder.                                              |
| C04 Confirm area  | Primary action at the reading-order end. Use a safe-area inset and make it reachable with keyboard and large text. |
| C05 Inline errors | Preserve input, focus first invalid field, announce the problem and provide a recovery action.                     |
| C06 Scoped list   | Virtualized stable keys, pull-to-refresh, focus retention and explicit load/retry when needed.                     |

Touch targets at least 48 dp Android / 44 pt iOS. Below 600 units use one column; 600–839 may add a navigation rail after fit checks; at 840+ propose a queue/detail split with 320 minimum for queue plus detail. The detail can become full width for picking or if long text, zoom, safe areas or keyboard constrain either pane. Avoid horizontal scrolling in task flow. Use native back gestures as a secondary option with visible actions. Disable decorative transitions with reduced motion.

Cached data always shows its recorded freshness. The shared state mapping for all screens is loading with a labeled progress indicator, empty with a context action, denied with safe navigation, stale with refresh, offline with local draft where allowed, field validation with preserved input, unexpected failure with bounded retry, and committed success with authoritative revision or receipt. Offline pack/handoff are protected from final submission. Localize screen text, labels, accessibility announcements and validation through the single bundled `public/orderflow.model.json`. Test locale parity, placeholders, RTL, long strings and fallback from the same validated bundled model.
